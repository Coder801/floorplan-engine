# Штроба — знаем, что в стене (пакет `floorplan_engine`, CLI `floorplan-engine`)

Инструмент делает DXF-чертежи (план помещения, электрика) из YAML-описания.
Распознавание фото и текста делаешь ты: читаешь фото или описание и пишешь `room.yaml` /
`electrical.yaml`. Код только валидирует YAML и детерминированно строит DXF и артефакт `.epd`
(листы для просмотра в браузере, canvas).
В ядре (`floorplan_engine`: схема, геометрия, DXF, отчёт) нет LLM и API-ключей — не добавляй их.
LLM есть только в анализаторе сервиса (`service/llm_analyzer.py`): `claude -p` по подписке
или Anthropic API по ключу. Его результат — тот же YAML, и он проходит ту же валидацию ядра.

**Правила перевода источников в YAML живут в двух местах:** разделы ниже (для тебя в этом
репозитории) и `service/analyzer_prompt.md` (для LLM-анализатора сервиса). Меняешь правило в
одном — меняй и в другом.

## Команды

```bash
uv run floorplan-engine check projects/<имя>                 # валидация, без файлов
uv run floorplan-engine build projects/<имя>                 # out/project.dxf + project.epd (без PNG)
uv run floorplan-engine estimate projects/<имя>              # смета электрики: out/estimate.md, .csv, .xlsx (формулы)
uv run floorplan-engine render-artifact projects/<имя>       # PNG листов из project.epd — для проверки
uv run floorplan-engine print projects/<имя> [--paper A3]    # PDF-альбом листов в натуральную величину
uv run floorplan-engine serve --data data/projects           # API сервиса (docs/service-api.md)
uv run floorplan-engine dev                                  # просмотр одной командой: API + страница http://127.0.0.1:5173
uv run floorplan-engine view                                 # только API просмотра projects/ (8000); пишет только wiring.yaml
uv run floorplan-engine access link projects/<имя> --owner <email>  # связать папку с базой (вход)
uv run floorplan-engine access invite projects/<имя> --role client  # ссылка-приглашение
cd web && npm install && npm run dev                    # только страница просмотра (API — view)
cd web && npm run build                                 # сборка фронта в web/dist (выкладка — README в web/)
cd web && npm run check && npm test                     # типы TypeScript и тесты фронта (vitest)
uv run floorplan-engine analyze projects/<имя>               # LLM-анализ source/ → YAML (подписка)
uv run floorplan-engine pdf-facts projects/<имя>/source/x.pdf # выжимка из векторного PDF без LLM (--json)
uv run floorplan-engine facts projects/<имя>/source/x.jpg   # выжимка из любого источника: вектор или растр
uv run floorplan-engine facts-bench projects/<имя>/source/x.pdf # точность растра против вектора
uv run floorplan-engine preview projects/<имя>               # PNG листов из DXF (отладка ezdxf)
uv run pytest && uv run mypy && uv run ruff check . && uv run ruff format --check .
docker compose up -d db && uv run alembic upgrade head  # база сервиса (docs/database.md)
```

Slash-команды: `/plan`, `/electrical`, `/check` (в `.claude/commands/`).

## Агенты и скиллы

Субагенты — в `.claude/agents/`, у каждого свои границы и порядок работы:

| Агент | Когда звать | Что может |
| --- | --- | --- |
| `developer` | новая функциональность, багфикс в коде | правит код, тесты и документацию |
| `reviewer` | проверить изменения перед тем, как считать их готовыми | только читает и сообщает находки |
| `refactor` | мёртвый код, дублирование, длинные функции | правит без изменения поведения: сверяет тесты, выжимку PDF, хеш `.epd` |
| `tester` | покрыть тестами непокрытые функции | пишет unit-тесты на синтетических данных |
| `ui-designer` | придумать или улучшить экран просмотра / кабинета | макеты вариантов, затем вёрстка в `web/` |

Общие правила для всех агентов: данные пользователя в `projects/` (YAML моделей,
`wiring.yaml`, `source/`) не правятся, `analyze` не запускается (тратит токены), картинки листов открываются, только
если кодом проблему не найти. Скилл `verify` (`.claude/skills/verify/`) — полная проверка
изменений без LLM: тесты, типы, линтер, регрессия выжимки PDF и раскладка листов кодом
(`scripts/check_layout.py`).

## Правила работы с проектами

1. **Фото: выписывай только размеры, которые написаны на фото.** Не оценивай размеры на глаз,
   не считай по пропорциям и плитке. Всё, что не видно, — вопрос в `intake.yaml` (см. ниже).
2. **Перед генерацией покажи таблицу** «стена → длина → источник (фото / текст / допущение)»,
   а также таблицу проёмов и вопросы из `intake.yaml` с их весом.
3. **После `build` запусти `render-artifact`, открой PNG нужных листов `out/artifact/NN-<лист>.png`
   (`01-plan`, `02-electrical`, `03-lighting`, `04-wiring`, `06-points`, `07-elevations`) (Read) и проверь сам** — это ровно то, что клиент
   увидит в браузере (решение 2026-10-23: PNG при сборке не пишутся). Замкнут ли контур, на месте
   ли проёмы (стена, сторона, ширина), читаются ли размеры и не налезают ли подписи.
   Только потом сообщай результат.
4. **При ошибке валидации не подгоняй числа.** Покажи невязку ΔX/ΔY и варианты из сообщения
   («стена w2: 4000 → 4100 мм») и спроси, какой размер неверный.
5. **Допущения перечисляй в ответе явно**: толщина стен по умолчанию, высоты электрики, всё,
   что взято не с фото и не из текста. Двери допущением не бывают: неясная дверь — вопрос
   (см. «Двери — типовых размеров» ниже).
6. **Рисунок от руки не разбираем** (решение 2026-10-23): эскиз или план, нарисованный от
   руки, — на бумаге, планшете, поверх фото. С него не выписываются ни размеры, ни точки, ни
   топология; `room.yaml` и `electrical.yaml` по нему не пишутся. В `intake.yaml` — источник с
   пометкой `note: "рисунок от руки — не разбирается"` и critical-вопрос на этап: «пришлите
   чертёж (PDF, DWG) или обмерный план». Если в проекте есть другие источники, работай по ним,
   а рисунок только перечисли в `sources`. Разбираются: векторный PDF, скан и фото чертежа,
   фото помещения с написанными размерами, текст.
7. **Один проект — одна папка `projects/<имя>/`.** Исходные фото и заметки кладутся в `source/`,
   результаты — в `out/`. Имя папки латиницей: `kv42`, `dacha-kitchen`.

## Векторный PDF: сначала выжимка

Для PDF из программы проектирования (не скан) запусти `uv run floorplan-engine pdf-facts <файл>`.
Код сам находит масштаб листа, размеры (подпись и длину размерной линии), цепочки с суммами
и надписи с координатами в мм. Правила те же, что в разделе «Выжимка из PDF» в
`service/analyzer_prompt.md`:

- координаты — мм в масштабе от левого нижнего угла листа; у каждого листа своё начало,
  совмещай листы по общему размеру;
- значение размера — подпись; «≠» (подпись расходится с чертежом) — вопрос с обоими числами;
- суммы цепочек и сверка с общим размером уже посчитаны;
- координата надписи — это место надписи, а не символа, к которому ведёт выноска;
- привязка, снятая по координатам, а не по подписи, — допущение с комментарием
  `# PDF, масштаб` и один общий вопрос на этап со списком таких точек;
- **черновой план по масштабу** (решение 2026-10-21): если масштаб найден, а длин части стен
  на листах нет, недостающие длины, толщины и проёмы снимаются с векторов, округляются до
  10 мм и помечаются `# PDF, масштаб`. Вопрос — один общий на этап `plan` (`severity: major`,
  без `target`) со списком таких стен: «подтвердите или пришлите обмер». Подписанный размер
  важнее снятого; расхождение больше 1 % — вопрос с обоими числами. Critical — только когда
  стен не разобрать или масштаба нет (скан, фото).

## Как переводить фото или текст в room.yaml

- Единицы — мм. Если на фото см или м, переведи и укажи это в таблице.
- `origin` — левый нижний **внутренний** угол комнаты. Стены идут **по часовой стрелке по
  внутреннему контуру**, первая — вверх от `origin` (левая стена).
- У каждой стены есть `id`, уникальный в комнате: новые стены нумеруй `w1, w2…` по обходу.
  У прямоугольника: w1 — левая, w2 — верхняя, w3 — правая, w4 — нижняя. Проёмы, точки, щит
  и ленты ссылаются на стену по `id` (`wall: w3`), не по номеру. Если стену потом добавили
  или убрали, `id` остальных не перенумеровывай: так сохраняются ссылки и привязки в DXF.
- `id` проёмов, точек, кабелей и LED-лент уникальны во всём проекте: `<комната>_<тип>_<n>`
  (`kitchen_door_1`, `kitchen_socket_3`), кабели — `cable_<n>`. `board` занят щитом.
- `turn` — **внутренний** угол между стеной и следующей: 90 — обычный угол,
  270 — входящий угол (Г-образная комната), 180 — стена продолжается прямо.
  Сумма `turn` = (n − 2) · 180.
- Размер на фото по внешней стороне стены — это не внутренний размер. Не пересчитывай молча:
  спроси или укажи явное допущение.
- Перед записью сам сложи проекции стен: сумма по X и по Y должна дать 0 (допуск 10 мм).
- Проём: `offset` — от **начала** стены (по направлению обхода) до **края** проёма.
  Для стены w3 прямоугольника (правая, идёт вниз) offset отсчитывается **от верхнего угла**.
- **Ширина двери — по приоритету** (решение 2026-10-27):
  1. размер, подписанный на чертеже — на любом листе (план, схемы демонтажа и монтажа стен,
     цепочки размеров); берётся как есть, даже если он не из ряда;
  2. типовой размер — проём в стене из ряда 600, 700, 800, 900, 1000 (дверей в 300 или 580
     не бывает): ближайший к разрыву, снятому по масштабу;
  3. расчёт от соседних стен — только если первых двух нет; тогда это допущение с вопросом.
  Сначала ставится дверь, потом от неё простенки: невязку и округление забирает простенок,
  а не дверь. Коробка, нарисованная в проёме, — не проём: меряй разрыв в стене без неё.
  Снятый разрыв, который не ложится на ряд (±30 мм), — вопрос.
- **Неясную дверь не рисуй** (решение 2026-10-27): если по источнику не понятно, есть ли
  дверь, какой ширины, где петли или куда открывается, — в `room.yaml` её не пиши, задай
  вопрос в `intake.yaml` (major, со всем, что известно: стена, примерное место).
  `hinge` и `swing` — только с символа двери на чертеже или из текста.
- **Углы квартиры — прямые** (решение 2026-10-27): `turn` — только 90, 180 или 270. Косых
  стен и скошенных стыков не бывает; угол, который на чертеже кажется не прямым, —
  погрешность чертежа. Явно косая стена в источнике — вопрос, а не другой `turn`.
- `bearing: true` — только если несущая стена указана явно; иначе не ставь и спроси.
- `ceiling_height` — высота потолка, только из источника. Нет её — не пиши: код возьмёт 2700
  и пометит как допущение на листе проводки.
- Соседние комнаты: общую перегородку описывай в обеих комнатах с одинаковой толщиной.
  Дверь — в одной из них (`type: door`), в другой — `type: opening` на том же месте.
  В соседней комнате стена обходится в обратную сторону:
  `offset_соседа = длина − offset − width` (пример: 3200 − 300 − 800 = 2100).
- `source`: `photo` | `text` | `measured`.
- `language` (`ru` | `uk`) — язык надписей на чертеже; `sheet` — поля штампа (см. README).
  Подписи в штампе (`signatures`) и обозначение не выдумывай — только со слов пользователя.
  Организация, стадия и подписи, общие для студии, — в `projects/studio.yaml` (профиль студии);
  в `sheet` проекта их не повторяй, пиши только то, что у проекта своё.

## Вопросы: intake.yaml и answers.yaml

- `intake.yaml` — что разобрано (`sources`), что известно об этапах (`stages`: например,
  `plumbing: { status: absent, note: "на листах нет сантехники" }`) и вопросы (`questions`).
  Формат и примеры — в README и в docstring `intake.py`.
- Вопрос про конкретное поле — с `target` по id (`rooms.kitchen.walls.w3.length`,
  `points.kitchen_socket_1.height`), `answer: value | choice | text` и `assumption` — что сейчас
  стоит в модели. Если одно значение входит в несколько полей (две стены прямоугольника,
  перегородка соседней комнаты), перечисли их в `also`.
- Вес вопроса с `target` считает код (`assess.py`). `severity` указывай только у общих вопросов
  без `target`: critical — без ответа этап не строится, major — влияет на геометрию, minor —
  уточнение.
- Все этапы, по которым есть данные, пишутся сразу (решение 2026-10-21): если план строится,
  хотя бы с вопросами и размерами по масштабу, `electrical.yaml` пишется в том же проходе,
  не дожидаясь ответов. Не писать электрику можно, только если `room.yaml` нет.
- Нет геометрии вообще (ни подписанных размеров, ни масштаба) — не выдумывай `room.yaml`:
  пиши только `intake.yaml` с critical-вопросами.
  Этап «мало данных» не строится, `build` выдаёт отчёт `out/report.md`.
- Ответы — в `answers.yaml` (`q1: 1800`, `q2: { accept: true }`, `q3: { text: "…" }`).
  Значение подставляется в `target` при загрузке. `room.yaml` и `electrical.yaml` с ответом
  не правь, пока пользователь не попросит перенести ответы в исходники. Текстовый ответ
  разбираешь ты: правишь YAML и закрываешь вопрос.

## Ручные правки проводки: wiring.yaml

`wiring.yaml` пишет просмотр (`view`, лист проводки → «Править трассы»): перетянутые линии
(`wires.<id>: { from, to, path }`, мм модели) и перенесённые коробки (`boxes.<id>: { room,
group, at }`). Потребители и щит не двигаются. Ты этот файл не пишешь и не правишь; при
сборке правка, у которой id теперь означает другую линию или коробку, не применяется —
предупреждение в отчёте. Удалить запись — вернуть автотрассу.

## Как переводить описание в electrical.yaml

- У каждой точки `id`. Точки на стене: `room` + `wall` (id стены) + `offset` (до **середины**
  символа) + `height` (обязательна).
  Светильник на потолке: `ceiling: [x, y]` — от `origin` комнаты.
- `controls` у выключателя (`switch`, `pass_switch`) — id светильников, выводов LED и лент,
  которые он включает; только если это видно в источнике (связи на плане освещения, подпись
  «вимикач бра»). Нет — не пиши: код выведет связь по группе, помещению и подписи
  выключателя (`note`: «бра», «стеля», «підсвітка кухні») и пометит «*» на листе «Освещение».
- `led_output` — только вывод под LED-подсветку. Вывод кабеля к технике (вытяжка,
  кондиционер, рушникосушка, бойлер, домофон) — `type: outlet` с `note`.
- Щит: `board` с `offset` до середины; ширина по умолчанию 300.
- `cables[]`: свой `id`; `from` / `to` — `board` или `id` точки.
- `mode` — раскладка электрики, если групп в источнике нет (решение 2026-10-25; по умолчанию
  `standard`). Группы из источника важнее режима — их не перекладывай.
  - `standard` — свет и розетки каждого помещения — своей группой; проход (коридор,
    передпокій, хол) — к соседней зоне; зоны совмещённого помещения (кухня-вітальня) делятся по
    подписям точек; санузлы — каждый своей группой, розетки в них — через УЗО; отдельные линии —
    кондиционеры, рушникосушка, тёплый пол, мощная техника (от 4 мм²). Выключатель — в группе
    света, которым управляет; проходные одной цепи — в одной группе.
  - `economy` — максимально бюджетно, меньше автоматов: свет — одна группа на квартиру (две,
    если точек больше ~60), розетки — кухня отдельно, остальные одной группой, санузлы — одной
    группой через УЗО; отдельные линии — только то, что без них нельзя (от 4 мм²: варочная,
    духовка, бойлер).
  - `proper` — «по правильному»: как `standard`, плюс розетки кухни — столешница и техника
    раздельно, каждый кондиционер и мощный прибор — своя линия. Детали режима — позже.
    В `proper` и в щите `premium` у каждой линии от щита свой автомат (решение 2026-10-28):
    группу по линиям проводки (коробка помещения или зоны, прямая линия) делит код —
    QF1 → QF1, QF1.2…; в `electrical.yaml` группы так не дроби.
  `check` предупреждает, если в `standard` или `proper` группа света или розеток охватывает
  несколько помещений.
- `groups` — группы щита по имени: `QF4: { name: "Розетки кухні", breaker: C16, rcd: "30 мА" }`.
  Только из источника; нет назначения — не пиши: код составит его по точкам («Розетки —
  Спальня*») для таблицы «Групи щита» на листе электрики. На чертеже у групп — только «QF4».
- `power` у точки — мощность потребителя, Вт, только из источника (паспорт, спецификация
  техники). Нет — не пиши: код возьмёт типовую по виду точки и `note` («духовка» — 3,5 кВт,
  розетка — 100 Вт на пост, варочная — 7,2 кВт) и пометит «*» на листе «Щит».
- `panel` — щит в лицо (лист «Щит», решение 2026-10-27). `scheme`: `economy` — мокрые зоны
  под одним УЗО, без реле напряжения, резерв ручным переключателем; `standard` — реле
  напряжения, мокрые зоны дифавтоматами, АВР; `premium` — плюс УЗИП, все группы
  дифавтоматами, характеристика B (моторная нагрузка — C). Не задана — по `mode`
  (`proper` → `premium`). `earthing` — TN-C-S (по умолчанию) или TN-S; TT и счётчик в щите —
  позже. `input` (А) и `power` (кВт) — только из техусловий или со слов заказчика; нет —
  ввод 63 А допущением. Резерв `backup: none | inverter | plug` — только из источника или
  ответа; не задан — гибридный инвертор допущением. `reserve: [QF1, …]` — группы резервной
  шины (нет — свет, холодильник, роутер, котёл, насос, ворота, розетки кухни). Фаза пока
  одна; три фазы — распределение по группам потребителей. Вопросы щита (`panel_*`:
  резерв, ввод, состав резерва, разделённые группы, кабель тяжёлого прибора) составляет код —
  в `intake.yaml` их не пиши; ответ `panel_split_*` — перенеси вторую линию в
  `electrical.yaml` отдельной группой и кабелем.
- `route: floor` у кабеля — группа идёт по полу в стяжке (подъёмы от пола, коробки на 300 мм,
  без сверления стен над дверями); иначе — по потолку. Ставь, только если это сказано.
- Отдельные линии без коробок (`direct`) код определяет сам: сечение от 4 мм², группа только
  из `outlet`, слаботочка. `direct: true` пиши явно для остального (регуляторы тёплого пола).
- `wet: true` у помещения в room.yaml — санузел, ванная, прачечная: коробки там IP44.
- Стандартные высоты (розетки 300, выключатели 900, щит 1700) — это **допущение**:
  подставляй, только если их нет в описании, и перечисляй в ответе.

## Код

Карта системы — кто что считает (код или LLM) и в какой функции — в `docs/architecture.md`.
Меняешь, где что считается, — правь и её.

- Python 3.11+, `uv`. Типизация везде, `mypy --strict` и `ruff` без ошибок. После правок
  запускай `uv run pytest`.
- Модули в `src/floorplan_engine/`:
  - `schema.py` — модели pydantic;
  - `geometry.py` — контур, невязка, площадь, внешние углы;
  - `validate.py` — правила и сообщения на русском с путём к полю; наложение ответов;
  - `intake.py` — схема intake.yaml / answers.yaml, пути к полям по id;
  - `assess.py` — вес вопросов и статус этапов (строить / мало данных / данных нет);
  - `report.py` — out/report.md и report.json;
  - `layers.py` — слои, стили, шрифт (IBM Plex Sans Light из `fonts/`), масштаб листа (`drawing_scale`, ряд `SCALES`; размеры «на листе» — `sheet()`);
  - `sheets.py` — документ проекта: модель 1:1 и листы (layouts): общие формат и масштаб, раскладка по четырём секциям с крестом в углу штампа (план | таблицы / легенда | штамп); таблицы, что не влезли над штампом, — колонками справа налево за счёт секции плана (`arrange`); смета этапа — на его листе (электрика — на листе проводки);
  - `tables.py` — таблицы на листе (экспликация помещений с полями площади);
  - `titleblock.py` — рамка листа, основная надпись (форма 3, блок с атрибутами), подбор формата;
  - `texts.py` — надписи на чертеже на `ru` / `uk` (поле `language` в room.yaml);
  - `draw_plan.py` — стены (общий силуэт через shapely, штриховка по материалу), проёмы,
    размеры, подписи;
  - `draw_electrical.py` — электрика, трассы, легенда;
  - `point_numbers.py` — номера точек на листе электрики (у символа только номер) и
    ведомость «Точки» отдельным листом в конце комплекта: одинаковые точки (вид, высота,
    примечание) — одной строкой со списком номеров;
  - `lighting.py` — план освещения, лист сразу за электрикой: связи «выключатель → свет»
    (`controls` или допущение по группе, помещению и подписи выключателя, «*»), свет одного
    набора — цепочкой, номера света (слой L-TEXT), таблица «Выключатели»;
  - `elevations.py` — развёртки стен: что на каждой стене с электрикой (проёмы, точки с
    номерами листа электрики, щит, коробки и штробы из `wiring.py`), вид изнутри; под заголовком —
    что за стеной (соседнее помещение и номер его стены или «вне квартиры»): у общей перегородки
    две развёртки, по одной с каждой стороны, и каждая называет другую; выводы соседа на
    обратной стороне — бледно, на своём месте; от вывода — пунктир к шкалам отступов и высот;
    `draw_elevations.py` — рисунок стены на листе со шкалами отступов и высот; листы
    «Развёртки» — в конце комплекта, по страницам (`sheets.elevations_spec`);
  - `labels.py` — размещение подписей без наложений: места вокруг символа со штрафами
    (подпись, символ, проём, лента, стена, чужое помещение), далеко — с выноской;
  - `specification.py` — спецификация изделий электрики (количество по модели);
  - `lines.py` — линия от щита — свой автомат: в `proper` и щите `premium` группа модели
    делится по линиям проводки от щита (QF1 → QF1, QF1.2…) до щита, проводки и таблиц;
    вызывает `validate` (модель отчёта и вопросы щита);
  - `groups.py` — таблица «Группы щита»: QF, назначение (из `groups` или составленное по
    точкам, «*»), кабель, точки, автомат (только из модели);
  - `panel.py` — щит в лицо: потребители по точкам (`power` или типовая по виду и `note`),
    нагрузка групп, автоматы (свет 10, розетки 16, тяжёлые — по току, не больше, чем держит
    кабель), перегруженная группа — линиями на щите (QF8, QF8.2), состав щита по
    `panel.scheme` (economy / standard / premium) и резерву (`panel.backup`), слабые места —
    на лист и в отчёт, вопросы этапа `panel` (`panel_questions`; составляет код, ответы —
    в answers.yaml, накладывает `validate.apply_auto_answers`); роспись `out/panel-loads.csv`;
    `panel_catalog.py` — каталог аппаратов: модели брендов (ширина в модулях, высота, вид),
    бренд щита — `panel.brand`; новые бренды — только по данным производителя;
    `draw_panel.py` — лист «Щит» для печати (DXF): щит в лицо прямо на листе (без видового
    экрана, по месту секции плана — `SheetSpec.body`), таблица аппаратов. В просмотре щит
    рисует свой компонент из ключа `panel` страницы (`panel.panel_data`), не из примитивов;
  - `estimate.py` — смета электрики: объёмы из модели (кабель, подрозетники, коробки,
    опрессовка, крепления, штробы, щит), цены — из `prices.yaml` проекта, а если его нет — из
    общего прайса студии `projects/prices.yaml` (`pipeline.find_prices`); без цены — «нет цены»,
    цены не выдумывай. Excel — `out/estimate.xlsx`: сумма строки и итоги формулами. Таблица сметы стоит на листе проводки (`estimate_table`; без прайса —
    ведомость объёмов без цен), отдельно — `out/estimate.md` и `.csv` (команда `estimate`);
  - `routing.py` — трассировка кабеля в обход стен, через дверные проёмы (сетка, путь
    с минимумом поворотов);
  - `wiring.py` — проводка через распаечные коробки: коробки, трассы, длины кабеля
    (из модели, не из DXF); `draw_wiring.py` — её лист, таблица и журнал `out/wiring-boxes.csv`;
  - `objects.py` — карточки объектов для подсказок просмотра (ключ `тип:id`, как в XDATA):
    линия проводки по смыслу «QF4: К3 → Розетка, Кухня», автомат, кабель, откуда-куда, длины;
    точки, коробки, щит, помещения, стены, проёмы. Пишутся в страницы `.epd` (`objects`);
  - `side.py` — таблицы листов для боковой панели просмотра (строка → объекты чертежа) и
    объекты темы листа для подсказок (`STAGE_OBJECTS`); пишутся в страницы `.epd` (`tables`);
  - `scene3d.py` — 3D-сцена проводки для просмотра (ключ `scene` страницы проводки `.epd`):
    стены с проёмами, трассы по высоте (подъём, путь по потолку или полу, спуск), точки,
    коробки, щит; новых расчётов нет — тот же `wiring.py`. Показ — `web/src/three/Scene3D.tsx`
    (react-three-fiber);
  - `symbols.py` — блоки УГО;
  - `ids.py` — ID объектов в DXF: XDATA `FLOORPLAN_ENGINE` (тип + id из YAML) на каждом примитиве
    модели; новый рисуемый объект оборачивай в `with tagged(msp, тип, id)`;
