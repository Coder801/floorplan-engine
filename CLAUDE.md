# Shtroba — знаем, что в стене (пакет `floorplan_engine`, CLI `floorplan-engine`)

Инструмент делает DXF-чертежи (план помещения, электрика) из YAML-описания.
Распознавание фото и текста делаешь ты: читаешь фото или описание и пишешь `room.yaml` /
`electrical.yaml`. Код только валидирует YAML и детерминированно строит DXF и артефакт `.epd`
(листы для просмотра в браузере, canvas).
В ядре (`floorplan_engine`: схема, геометрия, DXF, отчёт) нет LLM и API-ключей — не добавляй их.
LLM есть только в анализаторе сервиса (`service/analysis/llm_analyzer.py`): `claude -p` по подписке
или Anthropic API по ключу. Его результат — тот же YAML, и он проходит ту же валидацию ядра.

**Правила перевода источников в YAML живут в одном месте** —
`src/floorplan_engine/service/analysis/analyzer_prompt.md`, его же читает LLM-анализатор сервиса.
Здесь — только порядок работы: что запускать, что показывать и когда останавливаться.

## Команды

```bash
uv run floorplan-engine check projects/<имя>                 # валидация, без файлов
uv run floorplan-engine build projects/<имя>                 # out/project.dxf + project.epd (без PNG)
uv run floorplan-engine estimate projects/<имя>              # смета электрики: out/estimate.md, .csv, .xlsx (формулы) и состав работ out/work-scope.md; смету сантехники (out/plumbing-estimate.*) пишет build
uv run floorplan-engine render-artifact projects/<имя>       # PNG листов из project.epd — для проверки
uv run floorplan-engine print projects/<имя> [--paper A3]    # PDF-альбом листов в натуральную величину
uv run floorplan-engine serve --data data/projects           # API сервиса (docs/service-api.md)
uv run floorplan-engine dev                                  # просмотр одной командой: API + страница http://127.0.0.1:5173, оба перезагружаются при правках
uv run floorplan-engine view                                 # только API просмотра projects/ (8000); пишет только wiring.yaml
uv run floorplan-engine access link projects/<имя> --owner <email>  # связать папку с базой (вход)
uv run floorplan-engine access invite projects/<имя> --role client  # ссылка-приглашение
uv run floorplan-engine access code projects/<имя> --label "Иван" [--role client_code]  # код доступа без учётки: просмотр или заказчик — настраивает проект (codes, revoke-code)
uv run floorplan-engine project push projects/<имя> [--owner <email>]   # папку — в базу: новая версия модели, исходники, сборка (правда — база)
uv run floorplan-engine project pull <имя> [--to projects] [--force]    # из базы — в папку: модель, исходники, out/ последней сборки
uv run floorplan-engine project build [<имя>…] [--owner <email>]         # пересобрать из базы текущим кодом: модель не меняется, без имён — все проекты студии
uv run floorplan-engine project import projects --owner <email>         # перенести папку проектов и прайс/профиль студии в базу (studio push|pull — только студия)
cd web && npm install && npm run dev                    # только страница просмотра (API — view)
cd web && npm run build                                 # сборка фронта в web/dist (выкладка — README в web/)
cd web && npm run storybook                          # Storybook: компоненты по отдельности, http://127.0.0.1:6006
cd web && npm run check && npm test                     # типы TypeScript и тесты фронта (vitest); покрытие — npm run coverage
cd admin && npm install && npm run dev                  # админка платформы http://127.0.0.1:5174/admin/ (API — view, вход — в просмотре)
uv run floorplan-engine analyze projects/<имя>               # LLM-анализ source/ → YAML (подписка)
uv run floorplan-engine pdf-facts projects/<имя>/source/x.pdf # выжимка из векторного PDF без LLM (--json)
uv run floorplan-engine facts projects/<имя>/source/x.jpg   # выжимка из любого источника: вектор или растр
uv run floorplan-engine facts-bench projects/<имя>/source/x.pdf # точность растра против вектора
uv run floorplan-engine preview projects/<имя>               # PNG листов из DXF (отладка ezdxf)
docker compose up -d db && uv run alembic upgrade head  # база сервиса (docs/database.md), только Postgres
TEST_REQUIRE_DB=1 uv run pytest --cov && uv run mypy && uv run ruff check . && uv run ruff format --check . && uv run lint-imports
uv run python scripts/flow.py feature <имя> | integrate | release [--dry-run]  # ветки и релиз: develop → feature → develop → main (docs/development.md)
uv run python scripts/flow.py ship [--increment patch] [--rebuild]  # всё после /commit: вливание, проверки, релиз, пуш, пересборка
uv run python scripts/server.py check | rebuild [имена] [--wait] | send <проект> room.yaml  # боевой сервер через railway ssh
```

Slash-команды: `/plan`, `/electrical`, `/check`, `/review`, `/commit`, `/release` (в `.claude/commands/`).

## Агенты и скиллы

Субагенты — в `.claude/agents/`, у каждого свои границы и порядок работы:

| Агент | Когда звать | Что может |
| --- | --- | --- |
| `backend-developer` | новая функциональность, багфикс на бэке: ядро и `service/` (Python) | правит код, тесты и документацию |
| `frontend-developer` | новая функциональность, багфикс в просмотре `web/` (React + TypeScript) | правит фронт по раскладке компонентов, переводы, тесты и документацию |
| `reviewer` | проверить изменения перед тем, как считать их готовыми (`/review` — вместе со встроенным `/code-review`) | только читает и сообщает находки: правила Штробы, границы слоёв, детерминизм, документация |
| `committer` | закоммитить несохранённые изменения (`/commit`) | разбирает `git status` и `git diff`, делит на независимые коммиты, стейджит по явным путям и коммитит; сообщение по-английски; не пушит и историю не переписывает — пуш делает человек |
| `refactor` | мёртвый код, дублирование, длинные функции | правит без изменения поведения: сверяет тесты, выжимку PDF, хеш `.epd` |
| `tester` | покрыть тестами непокрытые функции | пишет unit-тесты на синтетических данных |
| `ui-designer` | придумать или улучшить экран просмотра / кабинета | макеты вариантов, затем вёрстка в `web/` |

Общие правила разработки для всех агентов и людей — `docs/development.md`: данные пользователя
в `projects/` (YAML моделей, `wiring.yaml`, `source/`) не правятся, `analyze` не запускается
(тратит токены), картинки листов открываются, только если кодом проблему не найти, тест и
документация — в том же изменении. Своё у бэка и фронта — в описаниях `backend-developer` и
`frontend-developer` (раскладка компонентов фронта — там и в `web/README.md`). Скилл `verify` (`.claude/skills/verify/`) — полная проверка
изменений без LLM: тесты, типы, линтер, регрессия выжимки PDF и раскладка листов кодом
(`scripts/check_layout.py`).

## Правила работы с проектами

1. **Фото: выписывай только размеры, которые написаны на фото.** Не оценивай размеры на глаз,
   не считай по пропорциям и плитке. Всё, что не видно, — вопрос в `intake.yaml`.
2. **Перед генерацией покажи таблицу** «стена → длина → источник (фото / текст / допущение)»,
   а также таблицу проёмов и вопросы из `intake.yaml` с их весом.
3. **После `build` запусти `render-artifact`, открой PNG нужных листов `out/artifact/NN-<лист>.png`
   (`01-plan`, `02-electrical`, `03-lighting`, `04-wiring`, `NN-plumbing`, `NN-points`, `NN-elevations`) (Read) и проверь сам** — это ровно то, что клиент
   увидит в браузере (решение 2026-10-23: PNG при сборке не пишутся). Замкнут ли контур, на месте
   ли проёмы (стена, сторона, ширина), читаются ли размеры и не налезают ли подписи.
   Только потом сообщай результат.
4. **При ошибке валидации не подгоняй числа.** Покажи невязку ΔX/ΔY и варианты из сообщения
   («стена w2: 4000 → 4100 мм») и спроси, какой размер неверный.
5. **Допущения перечисляй в ответе явно**: толщина стен по умолчанию, высоты электрики, всё,
   что взято не с фото и не из текста. Двери допущением не бывают: неясная дверь — вопрос
   (правила дверей — в `analyzer_prompt.md`).
6. **Рисунок от руки не разбираем** (решение 2026-10-23): эскиз или план, нарисованный от
   руки, — на бумаге, планшете, поверх фото. С него не выписываются ни размеры, ни точки, ни
   топология; `room.yaml` и `electrical.yaml` по нему не пишутся. В `intake.yaml` — источник с
   пометкой `note: "рисунок от руки — не разбирается"` и critical-вопрос на этап: «пришлите
   чертёж (PDF, DWG) или обмерный план». Если в проекте есть другие источники, работай по ним,
   а рисунок только перечисли в `sources`. Разбираются: векторный PDF, скан и фото чертежа,
   фото помещения с написанными размерами, текст.
7. **Один проект — одна папка `projects/<имя>/`.** Исходные фото и заметки кладутся в `source/`,
   результаты — в `out/`. Имя папки латиницей: `kv42`, `dacha-kitchen`.

## Как переводить источники в YAML

**Перед тем как писать `room.yaml`, `electrical.yaml`, `plumbing.yaml` или `intake.yaml`, прочитай
`service/analysis/analyzer_prompt.md`.** Там все правила: что брать из источника, что считать
допущением, какие вопросы задавать, поля и примеры YAML. Новое или изменённое правило перевода
пиши туда, сюда не копируй. Разница с анализатором одна: он работает без человека, а ты — с ним:

- раздел «Что ты возвращаешь» к тебе не относится: файлы пишешь сам, в папку проекта;
- из раздела «Раунды» действует всё про этапы: все этапы, по которым есть данные, пишутся сразу
  (решение 2026-10-21), не дожидаясь ответов;
- у векторного PDF выжимку получаешь сам: `uv run floorplan-engine pdf-facts <файл>`;
- вопросы всё равно идут в `intake.yaml`, а чего не хватает для решения — спроси в ответе
  (см. «Правила работы с проектами»).

## Ответы: answers.yaml

- Формат `intake.yaml` — в README и в docstring `model/intake.py`, правила вопросов — в `analyzer_prompt.md`.
- Ответы — в `answers.yaml` (`q1: 1800`, `q2: { accept: true }`, `q3: { text: "…" }`).
  Значение подставляется в `target` при загрузке. `room.yaml` и `electrical.yaml` с ответом
  не правь, пока пользователь не попросит перенести ответы в исходники. Текстовый ответ
  разбираешь ты: правишь YAML и закрываешь вопрос.
- Просмотр тоже пишет ответы (решение 2026-11-04, `POST /api/projects/{key}/answers`, право
  `answer`): строки `answers` правит код и оставляет комментарии рядом, кто и когда — в разделе
  `log`. Ответ, дающий новую ошибку проверки, не сохраняется. Текстовый ответ только
  сохраняется: чертёж не меняется, сборка не считается устаревшей; разбор — кнопкой после Б6.
  Разобранный (`resolved: true`) ответ можно изменить, но не снять.
- Ответ на вопрос `groups` — список групп модели, а не линий (`panel_reserve: [QF1, QF3]`): так выбор
  резервной шины переживает смену варианта. Такой вопрос строит только код (`panel_questions`).
- Вопросы делятся на вопросы студии и вопросы заказчика (`audience`, решение 2026-11-11). Ответ
  заказчика только уточняет: он хранится как `{ text }` и в модель не подставляется, чертёж
  меняется только по исходникам. Студия отмечает его «учтено» (`resolved: true`) или возвращает
  с комментарием (`returned`) — в просмотре, право `review`. Правила — в `analyzer_prompt.md`.
- `option_labels` у вопроса `choice` — подписи вариантов для заказчика, на языке проекта
  (`{ none: "Без резерва" }`): значения остаются машинными.

## Ручные правки проводки: wiring.yaml

`wiring.yaml` пишет просмотр (`view`, лист проводки → «Править трассы»): перетянутые линии
(`wires.<id>: { from, to, path }`, мм модели) и перенесённые коробки (`boxes.<id>: { room,
group, at }`), по вариантам проводки (`variants.<режим-трасса-разводка>`; правки без раздела —
у варианта «как в проекте»). Потребители и щит не двигаются. Ты этот файл не пишешь и не
правишь; при сборке правка, у которой id теперь означает другую линию или коробку, не
применяется — предупреждение в отчёте. Удалить запись — вернуть автотрассу.

`variant.yaml` — вариант проводки, выбранный в просмотре (`{ mode, route, distribution, path,
conduit, plaster, rough_light }`, `docs/wiring-variants.md`): режим, трасса, разводка, форма трассы,
гофра (нет, на потолке, на потолке и в стенах), монтаж кабеля до или после штукатурки, черновой свет; точки — из проекта. Его тоже пишет только
просмотр. Нет файла — вариант «как в проекте». Выбирают студия, хозяин «Моего ремонта»
и клиент студии — по приглашению или по коду заказчика (решение 2026-11-11); трассы руками правит только тот, у кого `edit_wiring`.

## Код

Где искать, прежде чем править:

- `docs/modules.md` — карта модулей бэка и фронта: что в каком файле и за какую функцию
  отвечает. Добавил, переименовал модуль или поменял, за что он отвечает, — правь строку там.
- `docs/architecture.md` — поток данных и кто что считает (код или LLM).
  Поменял, где что считается, — правь и её.
- `docs/development.md` — общие правила разработки; `web/README.md` — устройство и стили
  фронта; `docs/epd-format.md` — формат `.epd`; `docs/service-api.md` — API сервиса.

Правила:

- Python 3.11+, `uv`. Типизация везде, `mypy --strict` и `ruff` без ошибок. После правок
  запускай `uv run pytest`. Тесты — по папкам пакетов: `tests/<пакет>/test_<модуль>.py`
  (один файл на модуль), общие заготовки — `tests/conftest.py`.
- Пакеты `src/floorplan_engine/` — слоями, сверху вниз; выше может импортировать ниже, не
  наоборот (контракты import-linter в `pyproject.toml`, проверка — `uv run lint-imports`):
  `cli/` → `service/` (API `api/`, анализ `analysis/`, `facts/`, `db/`) → `pipeline/` →
  `epd/` (артефакт для просмотра) → `sheets/` (документ, печать, PNG) → `validation/` →
  `drawing/` (DXF) → `plumbing/` (сантехника) → `electrical/` (расчёты) → `model/` (схема,
  intake, надписи, контур). Сантехника выше электрики: берёт её трассировку
  (`electrical/routing.py`), цены и развёртки; электрика сантехнику не знает.
  Ядро (всё, кроме `service/` и `cli/`) не импортирует `service/`, LLM, сеть, базу и веб;
  `model/`, `validation/`, `electrical/`, `plumbing/` не импортируют ezdxf. Исключений из слоёв нет и не
  добавляй (`ignore_imports`) — общее для слоёв выноси вниз. Правила раскладки — агент `backend-developer`.
- Логику сборки держи в `pipeline/` (его вызывают и CLI, и сервис), `cli/` — только печать и
  коды выхода. Новый рисуемый объект оборачивай в `with tagged(msp, тип, id)` (`drawing/ids.py`).
  Меняешь смысл ключей `.epd` — повышай `FORMAT_VERSION`.
- Цены в прайсы не выдумывай; новые щиты и бренды в каталог — только по данным производителя.
- Импорты ezdxf — из модулей, где имена определены (`ezdxf.filemanagement.readfile`, а не
  `ezdxf.readfile`): так требует `mypy --strict`.
- Фронт — самостоятельный проект `web/` (React 19 + TypeScript + Vite), бэк для него — только
  API `service/api/viewer.py`. Строки интерфейса — только через `shared/i18n/` (ключ в `ru.ts`,
  `uk.ts`, `en.ts`); компонент — папка `ИмяКомпонента/` с `index.tsx` и `.module.scss`; правила —
  агент `frontend-developer`.
- Сообщения пользователю — на русском. Ошибка валидации всегда содержит путь к полю YAML.
