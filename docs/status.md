# Состояние проекта и план

Обновлено: 2026-10-28. Документ для того, чтобы продолжить работу на другом компьютере или
в новой сессии.

## Цель

Сервис для проектировщиков и монтажников. Пользователь загружает PDF, фото или эскиз.
Сервис разбирает источники, задаёт уточняющие вопросы, принимает ответы и собирает:

- `project.dxf` — модель 1:1 и отдельный лист на каждый этап, правится в AutoCAD;
- `project.epd` — артефакт для личного кабинета (отдельный сервис строит из него страницы JPEG).

Этапы проекта: план, мебель, освещение, розетки, проводка (с коробками), вода и канализация.

## Принятые решения

- **Модель проекта (YAML) — единственный исходник.** DXF и `.epd` — результаты сборки.
  Обратный перенос правок из DXF (`update`) — после MVP: он будет опираться на метки
  `FLOORPLAN_ENGINE` и атрибуты точек.
- **Модель листов — это DXF-документ в памяти.** Артефакт `.epd` выгружается из записанного
  DXF движком ezdxf, поэтому кабинет и AutoCAD показывают одно и то же.
- **Ядро без LLM.** LLM только в `service/llm_analyzer.py`. Правила перевода источников в YAML
  дублируются в CLAUDE.md и `service/analyzer_prompt.md`: меняешь одно — меняй другое.
- **Подписка — для разработки, API-ключ — для продукта.** По условиям Anthropic сторонний
  продукт не может работать через вход по подписке. После перехода на ключ — замеры токенов
  и цены по `usage.jsonl`.
- **Хранение в продакшене.** В базу данных уходят проекты, состояния, раунды, вопросы и ответы
  (строками таблиц) и расход LLM. Модель проекта (комнаты, стены, точки) остаётся одним
  документом: JSONB с версией на раунд, контракт — pydantic-схема. Файлы результатов — в
  объектное хранилище. YAML остаётся для работы в Claude Code (`/plan`, `/electrical`). Ядру
  нужен загрузчик «модель из словарей», `Storage` сервиса меняется на реализацию с базой.
- Нормы — ДСТУ (позже профиль ISO). Смета (кошторис) — отдельный документ. На чертеже —
  специфікація.
- Эталон оформления — `projects/381922.207.1992-МЗ1(12.10)РД!!! (2).dwg` (проект связи, не
  электрики). Разбор — `docs/reference-381922-MZ1.md`.

основу остальному. Почти всё здесь — работа анализатора, поэтому сначала нужен первый
настоящий прогон (раздел «Ждёт проверки»).

| # | Фича | Что меняем |
| --- | --- | --- |
| 1 | **Масштаб источника** | Для векторного PDF масштаб уже считает код (фаза 4.1); осталось записать его в `intake.sources[]`. Анализатор определяет масштаб каждого листа источника: по подписанной шкале, по подписанным размерам или по эталону, как делали вручную для nahirna-16 (13,568 мм/pt по шагу 1400). | 2 | **Данные из штампа источника** | Анализатор заполняет `sheet` (обозначение, объект, здание, стадия, организация) из штампа исходного листа. Это не выдумка, а перенос с источником. Подписи (`signatures`) по-прежнему только со слов пользователя. Правило — в CLAUDE.md и `analyzer_prompt.md` |
| 3 | **Источник для каждого значения** | В модель добавляется ссылка на источник: файл, страница, область `[x0, y0, x1, y1]` в долях страницы. Ссылка ставится у размеров стен и проёмов, точек, ответов на вопросы. Сейчас источник — только комментарий YAML. Сервис вырезает область из PDF в PNG (`GET /projects/{id}/evidence/{ref}`), кабинет показывает вырезку рядом с вопросом и значением. Делать вместе с переходом модели в JSON (поле, а не комментарий) |

Если трасс нет, длина считается по нашей ортогональной трассе в модели. Из длин получаются кабельный журнал и спецификация. Связано с этапом «Проводка» |

В сервисе: `POST /projects/{id}/sources` (новая ревизия), история ревизий в `rounds/` или в базе, отчёт «что изменилось» (diff моделей по id). Экономит токены |
| 6 | **Вопросы к проекту со ссылками** | Чат по проекту в кабинете: «какая высота розеток на кухне?», «почему кладовка 1783?». Ответ строится по модели, отчёту и источникам со ссылками на объекты (`o` в `.epd`) и на источник (№ 3). В сервисе: `POST /projects/{id}/ask` → ответ и ссылки. Только чтение, модель чат не меняет |

## Электрика: разводка и щит (решено 2026-10-21)

Решения пользователя:
- **Способ разводки выбирает заказчик**, поэтому строим несколько вариантов и сравниваем:
  - лучевая — от щита отдельный кабель к каждой точке или блоку;
  - через распаечные коробки — от щита к коробке группы в помещении, от коробки к точкам;
  - распайка в подрозетниках (шлейф) — кабель идёт от точки к точке группы.
- Запас кабеля — 15%.
- Спецификация — пока только количество, без марок и типов подрозетников (сделано, 4.2).
- **Однолинейная схема щита:** сначала как структура данных, потом — чертёж.

План:
1. **Варианты разводки** (через коробки — сделано, 4.4; дальше лучевая и шлейф, сравнение). В `electrical.yaml` — блок `wiring`: какие варианты строить,
   прокладка по умолчанию (`ceiling | floor | wall`), запас 0,15. В `room.yaml` нужна
   высота потолка (`ceiling_height`; нет — вопрос). Длина кабеля = трасса по плану
   (ортогональная, уже рисуется) + спуски по стене до высоты точки + выпуски на концах,
   × 1,15. Коробки ставит код: одна на группу в помещении, у входа под потолком. Выход:
   кабельный журнал и метраж по маркам для каждого варианта, таблица сравнения вариантов;
   лист трасс на вариант. Если трассы есть в источнике — берём их (фича Bidflow № 4).
2. **Щит как данные** — в основном сделано (4.38): `panel` в `electrical.yaml`, автоматы и
   УЗО по схеме, нагрузка, модули DIN, проверка «автомат защищает кабель». Не сделано:
   явная структура «кто кого питает» с `rating` / `curve` / `poles` вручную, три фазы, TT,
   счётчик. Исходный план: блок `panel` в `electrical.yaml`: вводной аппарат, УЗО, автоматы и
   дифавтоматы (`rating`, `curve`, `poles`, `leakage`), кто кого питает, какие группы.
   Группы связываются с точками через `group`. Код проверяет: у каждой группы есть
   автомат; сечение кабеля соответствует номиналу (предупреждение); считает число модулей
   DIN и подбирает щит по рядам. Выход: спецификация щита.
3. **Однолинейная схема — чертёж** по данным п. 2: отдельный лист (нужна, решение
   2026-10-27; пока есть только щит в лицо).
